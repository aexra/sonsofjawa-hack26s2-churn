# Проверка модели риска

Это ML-ядро, а не готовая панель. Миграции лежат в стандартном пути Flyway. `V1` содержит исходную схему, `V2` — только служебную схему модели без пользователей и аутентификации, `V3` — проверку параметров; номера необходимо согласовать при интеграции backend. В существующей среде с применённой историей Flyway версионные миграции не заменять.

Источник архитектуры и исходных SQL-эскизов: соседний репозиторий `docs-agents`, файлы `docs/risk-model.md`, `docs/sql/V2__core.sql`, `docs/sql/R__risk_model.sql`. `fixtures/organizer.json` дословно сохраняет синтетический набор `source/tmplt/data.json`: 10 аккаунтов, 30 услуг, 100 транзакций. `docs-agents` и `infra-prod` не изменяются.

## Запуск

Из корня `service`:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s apps/api/src/test/ml -p 'test_*.py' -v
```

Нужны Python 3.10+, Docker CLI и работающий Docker Engine. PostgreSQL 18 Alpine закреплён digest в тесте. Первый запуск может скачать образ. Тесты создают отдельный контейнер со случайным именем, без сети и опубликованных портов, с временной БД в tmpfs. Внешние БД, существующие контейнеры и пользовательские тома не используются. Контейнер удаляется после выполнения, включая ошибки тестов.

## Контрольная точка переноса

Воспроизводит исходную формулу из `docs-agents` на фиксированном времени `2026-10-19T15:00:00Z`: 3 high, 1 medium, 2 low, 4 без оценки; сумма `expected_loss` 719520 евроцентов. Проверяет изменение весов, повторное применение модели с сохранением настроек, отсутствие оценки, удаление аккаунта и границы результатов.

Эти результаты относятся к первому коммиту переноса и подтверждают воспроизведение исходного SQL, а не качество прогноза. Текущие эталоны ниже изменены осознанно после исправления допущений.

## Текущая модель

Score — эвристический приоритет внимания от 0 до 100, не вероятность ухода. Шесть признаков нормированы в 0..1. Веса по умолчанию: необеспеченное продление 25, нехватка средств 25, ожидание оплаты 30, выключенные услуги 10, удалённые услуги 5, просроченные продления 5. Формула `100 × Σ(weight × feature) / Σ(weight)`; веса относительные, повышение одного веса уменьшает относительный вклад остальных. Пороги medium/high остаются 25/50. Пороги не подгоняются под распределение демонстрационного набора.

- Доступные средства `F = balance + bonusBalance`, если бонусы unlocked; при locked учитывается только balance. `withdrawBalance` — отдельный реферальный баланс: не вычитается из основного, не прибавляется без фактического перевода, не считается намерением уйти. Признак withdrawable_share и соответствующий вес удалены.
- История удалений: `deleted / (active + suspended + prolong_wait + deleted)`. Blocked исключён из числителя и знаменателя: причина блокировки неизвестна. Удаление остаётся слабой гипотезой, а не доказательством добровольного ухода.
- Технический ключ payment_failures сохранён для совместимости, отображаемое название — «просроченные продления». Считаются только prolong действующих услуг с возрастом от payment_overdue_hours включительно до payment_lookback_days исключительно. По умолчанию 24 часа и 30 дней; минимум 2 подходящих транзакции. Признак — доля not_performed среди таких транзакций. Свежие транзакции, order, будущие и слишком старые записи исключаются; завершённые продления входят в знаменатель на тех же условиях возраста. Недостаток транзакций означает нулевой вклад этого признака, а не отсутствие всей оценки.
- Порог зрелости транзакции и её выход из окна входят в valid_until. Максимальный возраст оценки по умолчанию 6 часов покрывает непрерывное изменение срочности между границами. В real/shifted планировщик должен ставить просроченные оценки в delta; frozen предназначен для воспроизводимых тестов.
- Платежи учитываются на полуоткрытом горизонте `[as_of, as_of + H)`: `n = ceil((H - days_left) / T)`, если days_left < H. Платёж точно на правой границе не включается.

## Деньги и контракт

`R = Σ(price × H / T)` по active/suspended/prolong_wait — нормированная тарифная выручка за горизонт, не календарный план денежных поступлений. Месяц принят за 30.4375 дня, год за 365.25; календарные границы и уже оплаченные периоды отдельно не моделируются. Suspended продолжает приносить выручку. R_auto — соответствующая выручка услуг с autoProlong вне prolong_wait. `S = min(R_auto, F)`, `L = round(score / 100 × max(R - S, 0))`.

`S` — условное покрытие доступными средствами, а не банковская гарантия списания. Бонусы могут покрывать услуги, но не являются новым денежным поступлением. `L` — «оценка выручки под риском»: эвристический сценарный показатель, не математическое ожидание убытка и не измеренная вероятность оттока.

Поле expected_loss сохранено для совместимости с черновиком API, но UI и метрики должны использовать указанную семантику. `model_metadata_vw` отдаёт score_kind, probability_calibrated=false, money_estimate_kind, валюту EUR, масштаб 100 и готовые пояснения. `churn_forecast_vw` отдаёт risk_weight вместо probability: суммы весов не следует называть ожидаемым числом уходов. Для калиброванного прогноза нужны реальные последующие исходы, временная валидация и проверка калибровки.

## Интеграция с backend

Применять V1, V2, V3 и повторяемую R__ в транзакциях Flyway. При изменении R__ появляется новая ревизия и все аккаунты попадают в delta; настройки сохраняются. Нельзя механически заменять существующие golden-значения числами из старой документации. Новые результаты описаны здесь, соседний docs-agents остаётся без изменений.

Валидация UPDATE настроек на стороне БД проверяет ненулевую сумму весов, medium < high, окно платежей больше порога просрочки, целочисленность количества транзакций и индивидуальные диапазоны. Связанные настройки следует менять одним UPDATE, API обязан дополнительно проверять неизвестные ключи и права доступа. Новые ключи настроек и причины должны передаваться динамически из каталога.

Сохранять model_version, as_of и calculated_at с каждой оценкой. Текущие оценки пересчитывать после изменения модели, исторические строки оставлять со своими версиями. Поля scores_delta_vw и customer_scores_vw совместимы с исходным эскизом; изменение колонки прогноза probability → risk_weight требует учёта в будущем обработчике графика.
